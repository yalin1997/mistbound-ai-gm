# 霧海紀事 MVP 獨立驗收與試玩報告

日期：2026-11-10。驗收者：獨立 subagent `/root/independent_acceptance`，並非原實作者。這是模型設計與操作的自動化試玩、規則對照及畫面檢查，**不是真人玩家研究**。

## 結論

**純規則單人／合作原型可進入受邀試玩，但尚不足以通過「AI GM 遊戲可行性」驗收。** 本輪自行設計的四條瀏覽器流程全部完成；另重現兩項 P2 規則一致性缺陷與一項獎勵設計風險。沒有發現本輪流程中的存檔遺失、舊檢定重擲或角色越權。真實模型未配置，不能據此推論自由敘事品質、延遲、成本與長期樂趣。

本輪依使用者指示只驗收，**未修復產品程式、未部署、未推送**。

## 受測版本、環境與方法

- 提交：`2e496f8734bbdc9a071cb11201c86a5bd249b4c0`。受測產品沒有未提交修改；僅增加 `acceptance/` 內的驗收產物。
- Linux、Node.js 24.22.1、Playwright 使用系統 `/usr/bin/chromium`，React 正式版靜態輸出搭配真實 Express／Socket.IO／SQLite。
- 先確認原服務 `http://127.0.0.1:3001/api/health` 回報 `rules`。正式服務及其玩家資料未修改。
- 另於 port 3201 啟動相同產品程式，使用驗收專用 SQLite 與合成帳號。瀏覽器單人使用**伺服器真實隨機骰**，沒有改骰點或跳過任務旗標。雙人用兩個隔離 context、不同帳號及真實 HTTP／WebSocket。
- 多人斷線寬限設定為 **600 ms** 以加速測試，實際等待約 1.8 秒；不是生產設定 60 秒的長時間驗證。
- 迷茫、金幣與章節順序另外用記憶體 SQLite、產品 Engine 與固定骰點測試介面重現。這些是可重現的規則探測，**不是自然骰機率或真人試玩成果**。
- 使用 workflow-skills 的 `work-verify` 與共用工程原則，對照 README、docs/rules.md、原始需求。沒有把原作者的 22+2 測試結果當成本輪獨立通過證據。

重跑命令（在 `/workspace/ai-gm-game`）：

```bash
node --import tsx acceptance/run-independent.ts > acceptance/evidence-run.log 2>&1
node --import tsx acceptance/probe-order.ts
```

第一支腳本自行啟動／關閉 port 3201 的隔離服務，須保持該 port 空閒。每次建立新的驗收 SQLite；資料含合成帳號登入資料，因此 `.gitignore` 排除 SQLite。兩個腳本都不需要模型金鑰。

## 可重現缺陷

### B1 · P2：迷茫可藉由防禦清除，未留到下一次檢定

規格依據：README 與 rules.md 均寫自然 1 讓「下一次檢定 -2」；畫面也顯示「下一次檢定 -2」。

重現：

1. 海岸人，洞察基本 2，種族加值 +1，正常觀察加值為 +3。
2. 觀察自然 1，HP 22→20、迷茫狀態變為 1。
3. 下一次行動選「防禦」，不擲骰。
4. 再建立一次觀察檢定。

期望：第一次後續檢定為 +1（2+1−2）。

實際：防禦後迷茫已為 0，後續觀察為 +3。無須承受另一個檢定即可規避懲罰。程式 `server/engine.ts` 的 endTurn 約第 778 行對每次行動都扣狀態，沒有只在檢定結算後扣除。

影響：特殊失敗的懲罰與顯示規則不一致，玩家可用安全區的一次防禦繞過。這不是阻斷任務的 P1；建議受邀測試前修正，並加入「大失敗 → 非檢定行動 → 檢定」回歸案例。

證據：`results.json` 的 confusion probe，expected +1、actual +3。

### B2 · P2：接續第二章後，探索仍沿用戰鬥順序

規格依據：rules.md 說探索依入房順序，戰鬥則由發起者先手、其餘按敏捷。

重現（三人、固定自然 20，無直接改遊戲狀態）：

1. 甲、乙、丙依序入房，建角開始。
2. 甲交談、乙提議移動濕地並全員同意、丙觀察、甲提議移動燈塔並全員同意。
3. 乙發起攻擊，戰鬥順序變為乙、甲、丙；甲使用技能、丙普通攻擊擊敗守衛，再由乙完成燈室互動。
4. 房主甲點擊接續第二章。

期望：回到第二章探索時依公開規則恢復甲、乙、丙，或明確告知採另一種探索順序。

實際：第二章保留乙、甲、丙，首位行動者為乙。`next` 分支（engine.ts 第 493–503 行）只重設 turnIndex，未恢復 turnOrder。

影響：不會讓任務無法完成，但初始順序由上一章戰鬥發起者改變，與規則契約不符。建議獨立探索與戰鬥順序，或明確修改規則並在切換時顯示。

證據：[probe-order.ts](probe-order.ts)、`order-probe.json`：initialJoinOrder=[序甲,序乙,序丙]、secondChapterOrder=[序乙,序甲,序丙]。

## 設計風險與試玩觀察

### R1 · P2 設計／經濟風險：已調查場景仍能反覆產生暴擊金幣

以自然 20 重複觀察港口 12 次，只有一份必要線索，金幣卻持續增至 36。現行公開規則本來就規定每次大成功額外 3 金幣，因此**這是符合目前實作與規則的設計風險，不列實作 bug**。固定骰只展示沒有場景獎勵上限，不代表真實玩家每次都能擲出 20；自然 1 仍有 HP 懲罰。

若金幣未來可用於跨場次經濟、購買或付費權益，重複低風險檢定缺乏場景掉落預算會影響平衡。可考慮同一可搜物件只發一次額外獎勵，後續大成功改提供其他有界結果。目前金幣沒有消費系統，實際營運影響尚未量測。

### R2 · 內容厚度與選擇影響尚未證實

本輪直接和平路線只需四次成功檢定與兩次移動即可完成第一章。劇情有清楚目標、線索及兩種通過守衛的方法，足以證明狀態機可以跑通；尚不足以支持規劃中的 30–60 分鐘內容目標。自動操作速度不能代表真人遊玩時長，也不能反推再玩意願。

港口的觀察、交談、調查都導向同一必要線索；第二章沿用相同區域與通過條件。這有利於原型穩定，但玩家選擇的後續差異有限。職業差異主要是屬性與數值，尚非不同玩法。建議下一輪先增加一個會改變 NPC／場景旗標與後續敘事的選擇，再擴充更多地圖或美術。

### R3 · 介面適合規則試玩，尚待真實裝置評測

手機三分頁可操作且沒有溢出，擲骰及待確認狀態清楚。桌面地圖與故事／角色並列，能看見正式數值結果。文字偏小、低對比與多個小型快捷按鈕是否影響長時間閱讀／觸控，需要實體裝置及不同視力使用者測試；本輪未作無障礙標準稽核。
